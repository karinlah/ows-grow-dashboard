# OWS — דשבורד הרשמות Grow

דשבורד פרטי שמראה **סך הכל הרשמות, סך הכל הכנסות, ופילוח פר מוצר** — מנתוני Grow.

בנוי על אותה תשתית בדיוק כמו `ows-crm`: Node + Express + SQLite (`better-sqlite3`),
התחברות עם `express-session` ו-`bcryptjs`, פרונטאנד וניל ללא framework וללא שלב build,
ופריסה ל-Render עם דיסק קבוע. העיצוב לקוח ממערכת העיצוב של האתר (`website/brand.css`) —
אותם צבעים, אותם פונטים, אותו סגנון.

## מאיפה מגיעים הנתונים

שני מקורות, שתופרים יחד תמונה אחת:

| מקור | תקופה | למה |
|---|---|---|
| **ייצוא רשמי מ-Grow** (`data/17-sep-grow-transactions.xlsx`) | הכול עד 17.9.2026 | חלק ממיילי התשלום הישנים כבר נמחקו מהתיבה — אי אפשר לשחזר את ההיסטוריה מהמייל |
| **מיילי "בוצע תשלום עבור בעל העסק"** | מ-17.9.2026 והלאה | נקלטים אוטומטית כל 15 דקות |

**אין ספירה כפולה.** מפתח הזיהוי של עסקה הוא ה**אסמכתא**, שמופיעה גם בייצוא וגם במייל,
והיא `UNIQUE` בטבלה. לכן הסריקה חופפת בכוונה על יום הייצוא עצמו (הוא נלקח באמצע היום,
ועסקאות מאוחרות יותר באותו יום קיימות רק במייל) — והכפילויות פשוט נדחות.

## איך מזוהה מוצר

השדה `עבור שירות:` במייל הוא **שם עמוד המכירה**, לא שם המוצר. הוא מפוצל לשניים:

```
"28.9 בשעות 18:00-20:30 מאסטר קלאס קלוד קוד"
         ↓
מוצר = "מאסטר קלאס קלוד קוד"   מועד = "28.9 בשעות 18:00-20:30"
```

כך שלושת עמודי המכירה (16.9 / 28.9 / 21.10) מתאחדים למוצר אחד עם שלושה מועדים.
זה נדרש כי ב-Grow עצמו שם המוצר לא עקבי — אפילו בתוך אותו עמוד מכירה
(בעמוד 28.9: 32 עסקאות רשומות כ"מאסטר קלאס קלוד קוד" ו-11 עם התאריך בשם).

**כתובת המייל של הלקוחה** מגיעה בחלק מהמיילים כטקסט רגיל אחרי `מייל:`, ובחלק
רק כקישור `mailto:` בתוך ה-HTML — ואז השורה נראית ריקה. הפרסור נופל חזרה לקישור,
אחרת הלקוחה נכנסת בלי זיהוי. יש על זה בדיקה ב-`npm test`.

### למה הפרסור לא סומך על שורות

ל-Grow אין פורמט אחד. בחלק מהמיילים השדות מופרדים ב-`|`, ובחלק הטקסט זורם
ברצף ונשבר לפי רוחב — ואז השבירה נופלת איפה שבא לה, כולל באמצע ערך:

```
אסמכתא: 517737452 עבור שירות:        ← שני שדות על שורה אחת
28.9 בשעות 18:00-20:30 ... בברכה,     ← והערך יחד עם החתימה

עבור שירות: מנוי                      ← וכאן הערך עצמו נשבר
מתחדש OWS בברכה,
```

לכן כל שדה נשלף עד ה**תווית הבאה** (`STOP_WORDS` ב-`growParser.js`), ולא עד סוף
השורה. זה לא ניקוי קוסמטי: כשהאסמכתא נשלפה כ-`"517737452 עבור שירות:"` היא
הפסיקה להתאים לאסמכתא שבייצוא, ההגנה מפני כפילויות נפלה, ועסקאות נספרו פעמיים.
שתי הצורות נמצאות כבדיקות ב-`npm test`.

## הרצה מקומית

```bash
npm install
npm run seed     # פעם ראשונה בלבד — טוען את הבסיס מהייצוא
npm start
```

עולה על http://localhost:3100 · כניסה: `hello@onewomanshowacademy.com` / `ows`
(ניתן לשנות ב-`.env` — ראי `.env.example`).

> `npm run seed` בונה מחדש את שורות הייצוא בלבד. עסקאות שנקלטו ממייל לא נמחקות.

## חיבור תיבת המייל

הקליטה עובדת ב-IMAP עם **סיסמת אפליקציה** של גוגל — בלי פרויקט Google Cloud
ובלי מסך הרשאות. קריאה בלבד: המערכת לא מוחקת ולא משנה שום מייל.

1. ליצור סיסמת אפליקציה ב-[myaccount.google.com/apppasswords](https://myaccount.google.com/apppasswords).
2. למלא `IMAP_USER` (כתובת הג'ימייל) ו-`IMAP_PASS` (סיסמת האפליקציה) —
   מקומית בקובץ `.env`, ובפרודקשן בלוח הבקרה של Render.
3. להפעיל מחדש. מכאן זה רץ לבד כל 15 דקות.

הסיסמה נשמרת רק בהגדרות השרת — לא בקוד ולא במסד הנתונים.
עד שהיא מוזנת הדשבורד עובד רגיל ומציג את נתוני הייצוא, עם התראה שהקליטה כבויה.

## פריסה ל-Render

`render.yaml` מגדיר שירות web בתוכנית Starter עם דיסק קבוע ב-`/var/data`, בדיוק
כמו ב-`ows-crm`. בעלייה ראשונה על דיסק ריק `prestart` זורע את הבסיס לבד.

**פעם אחת:**

1. [github.com/new](https://github.com/new) → repo **פרטי** בשם `ows-grow-dashboard`,
   בלי README/gitignore/license.
2. ```bash
   git remote add origin https://github.com/karinlah/ows-grow-dashboard.git
   git branch -M main && git push -u origin main
   ```
3. ב-[dashboard.render.com](https://dashboard.render.com) → `New` → `Blueprint` →
   לבחור את ה-repo. Render קורא את `render.yaml` ומקים את השירות והדיסק לבד.
4. במסך שנפתח למלא את ארבעת המשתנים המסומנים `sync: false`:

   | משתנה | ערך |
   |---|---|
   | `IMAP_USER` | כתובת הג'ימייל שאליה מגיעים מיילי Grow |
   | `IMAP_PASS` | סיסמת האפליקציה (לא הסיסמה הרגילה) |
   | `ADMIN_EMAIL` | האימייל לכניסה לדשבורד |
   | `ADMIN_PASSWORD` | הסיסמה לכניסה לדשבורד |

   `SESSION_SECRET` נוצר אוטומטית. אין צורך לגעת ב-`DB_PATH` ו-`NODE_ENV`.
5. `Apply` / `Deploy`. הבנייה לוקחת דקה-שתיים, ואז הכתובת שמתקבלת היא הדשבורד.

**מכאן והלאה:** `git push origin main` מפרסם אוטומטית. במהלך הדיפלוי יש כמה
שניות של 502 — זה נורמלי ולא אומר שמשהו נשבר.

**מה לבדוק אחרי הדיפלוי הראשון:** להיכנס לטאב "קליטת מיילים" ולוודא שכתוב
"מחובר · כל 15 דקות" ושהשליפה האחרונה רצה בלי שגיאה.

## פרטיות

`data/*.xlsx` לא נכנס ל-git, אבל `data/baseline-2026-09-17.json` **כן** — הוא נדרש כדי
שהמערכת תעלה עם הנתונים בדיפלוי ראשון, והוא מכיל שמות, מיילים וטלפונים של הלקוחות.
**המאגר חייב להישאר פרטי**, בדיוק כמו `ows-crm` שמכיל פרטי משתתפות ב-`db/seed.js`.

## מגבלות ידועות

* **זיכויים לא מנוכים אוטומטית.** מייל "בוצע תשלום" נשלח בעת החיוב; ביטול מגיע
  כ"חשבונית זיכוי" נפרדת שאין בה סכום או מוצר. עסקה שזוכתה בייצוא מסומנת
  `credited`, לא נספרת בהרשמות ולא בהכנסות, ומוצגת כהתראה.
  *(בייצוא של 17.9 יש אחת כזו: קורל הרוש, 450 ₪.)*
* **ההכנסות ברוטו**, לפני עמלות סליקה. "נטו לבנק" מוצג רק כשהוא ידוע — כלומר
  לעסקאות מהייצוא. המייל לא מדווח עמלה, ולכן לעסקאות שנקלטות ממנו הנטו יישאר 0
  עד שיטען ייצוא עדכני.
* מיילים שהפרסור נכשל עליהם נשמרים ב-`ingest_failures` ומוצגים בטאב "קליטת מיילים" —
  כדי שלא ייעלמו בשקט.

## שדרוגים אפשריים

* **Webhook מ-Grow** — בעמוד התשלום אפשר להגדיר כתובת callback שתדחוף כל עסקה
  לכאן מיידית במקום להמתין למייל. מדויק יותר וכולל גם זיכויים.
* **העלאת ייצוא מהממשק** — כדי לרענן את שדות העמלה/נטו ולסגור פערים, בלי הרצת סקריפט.
